# Stage 6 production security and privacy

Production uses college OIDC authorization-code PKCE for dashboard and Android. The backend exchanges codes only at the configured HTTPS token endpoint and verifies RS256-signed JWT API access tokens using the configured HTTPS JWKS URL, exact issuer, API audience, time claims and `sub`. Roles and course access come only from provisioned database records. Demo credentials are accepted only when `APP_ENV=development`, `ENABLE_DEV_AUTH=true` and `DEV_PASSWORD` are set; production login routes fail closed. For deployment, the identity provider must issue a signed **access token** with a dedicated FocusLock API audience and allow the dashboard and Android public-client redirect URIs. Provider-specific audience/scopes and real callback behavior require college testing.

The first admin is bootstrapped with `python -m app.provision_admin --subject ... --email ... --name ...` only on an empty production user table, after an operator verifies the exact issuer subject. Further users are provisioned by the admin API. Teachers cannot become admins or access courses they are not assigned. Admin receiver/user/device operations and teacher session/resource/privacy decisions are audited. Attendance corrections retain actor, previous/new status and reason. A compromised administrator or database remains a material risk; audit records are in the same database, not immutable external storage.

Students enroll a P-256 Android Keystore key via a single-use authenticated server challenge. Production accounts may register one active device; replacement requires signatures from both old and new keys over `FL-REPLACE1\nstudent_id\nold_device_id\nchallenge_id\nnonce\nnew_key_sha256_hex`. If the old device is lost, an administrator can revoke it with a reason, after which the student may enroll a new key. Revoked keys fail future check-ins. This does not prove a device is uncompromised. QR and device challenge rules remain in [QR protocol](QR_PROTOCOL.md).

Play Integrity verification is behind `PLAY_INTEGRITY_MODE=off|optional|required`. The server issues `integrity_request_hash` with registration and check-in challenges. Its exact value is base64url-no-padding SHA-256 of UTF-8 `FL-INTEGRITY1\n` + action (`register` or `checkin`) + `\n` + the canonical Stage 2 signed payload. The token is decoded only by Google's service, then the backend checks package name, exact request hash, age ≤120 seconds, `PLAY_RECOGNIZED`, and `MEETS_DEVICE_INTEGRITY`. Token digests have a unique database key and are retained briefly to reject replay. In `required` mode a missing/unsupported verdict blocks **device registration or QR**, while teacher-confirmed attendance remains available. In `optional` mode a missing verdict is allowed and does not become proof of trust. The Android client currently does not obtain a real Play Integrity token because a linked Play/Cloud project and credentials were unavailable; keep `required` off until that client path, end-to-end Google decoding and fallback UI are validated. Integrity results are never proof of identity, classroom presence or absence of cheating. See [Play Integrity standard requests](https://developer.android.com/google/play/integrity/standard).

Optional feature consent records keep student, feature, disclosure version, grant and withdrawal time. The app requests a server record before enabling BLE or VPN online; a local Pause/Exit always works offline. If withdrawal cannot reach the server, the app stores a private pending withdrawal and retries after sign-in or the next online class refresh. Until that retry succeeds, the server row may temporarily show consent, but BLE advertising and the local VPN stop immediately; server-side Bluetooth withdrawal expires outstanding credentials when received. Students see their attendance history and may request correction or deletion. A teacher can review course-scoped requests, but corrections use the separate audited attendance control and deletion requires institutional policy review. No request silently changes attendance.

The retention job removes focus events after `RETENTION_EVENT_DAYS` (default 30), raw BLE sightings after `RETENTION_SIGHTING_DAYS` (default 7), expired BLE credentials after `RETENTION_CREDENTIAL_DAYS` (default 1, once sightings no longer reference them), and stale challenges, integrity receipts, rate attempts and demo tokens. It does not automatically delete attendance or audit records; set their schedules with the institution. `python -m app.retention` runs directly, and `/internal/retention` requires a `CRON_SECRET` of at least 16 characters for a cloud scheduler. Neither handler logs request bodies or tokens. Docker API access logs and dashboard Nginx access logs are disabled; platform/provider logs must also be configured to exclude authorization headers, query strings, tokens and student data.

Database-backed rate limits cover development login, device/check-in challenges, OIDC code exchange, Bluetooth sightings/heartbeats, consent changes, privacy requests and device replacement. PostgreSQL advisory transaction locks serialize counters per window; a distributed WAF or reverse-proxy limit is still prudent for unauthenticated malformed requests. Inputs use Pydantic bounds, strict extra-field rejection on new sensitive endpoints, exact course/room/role checks and DB uniqueness constraints. CI runs Python/npm dependency audits and Dependabot watches dependency manifests; dependency reports were not available in the offline workspace.

Remaining risks: QR forwarding/collusion, BLE relay and receiver theft, privileged database/admin access, provider outages, backup/retention policy, a custom-scheme Android callback collision, Play Integrity gaps until external integration, an OIDC issuer that returns opaque rather than JWT API access tokens, and physical-device VPN/BLE/carrier behavior. No legal compliance or app-store approval is claimed.
