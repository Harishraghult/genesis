# Vercel deployment target (prepared, not published)

The requested cloud target is Vercel. Current [Vercel Services documentation](https://vercel.com/docs/services) describes a beta single-project frontend plus FastAPI setup; [Vercel's routing docs](https://vercel.com/docs/services/routing) state that services receive the original `/api/...` path. This repo therefore mounts FastAPI at `/api` in `backend/vercel_app.py` and routes `/api/*` to the Python service in root `vercel.json`. The dashboard uses same-origin `/api`, so browser tokens do not need cross-origin storage. The daily cron targets `/api/internal/retention`. This configuration is untested on a live Vercel account and may need adjustment as the beta changes.

## Quick demo with mock data (no database)

For a test deployment without any database server, set the variables in [`.env.vercel-demo.example`](../.env.vercel-demo.example) (`MOCK_DATA=true`, `APP_ENV=development`, `ENABLE_DEV_AUTH=true`, a strong `DEV_PASSWORD`, the signing keys) and leave `DATABASE_URL` unset. On each cold start the API builds a SQLite file in `/tmp`, creates the schema and seeds the demo accounts and classes. There is no migration step. Limits: changes disappear when the function restarts, and parallel function instances do not share data, so a teacher and a student can occasionally see different state. Use it for demos only, never with real student data. `APP_ENV=production` refuses to start with `MOCK_DATA`.

## Production with a managed database

1. Obtain a Vercel project and a managed PostgreSQL database, for example a [Vercel Marketplace Postgres integration](https://vercel.com/docs/marketplace-storage). Use a TLS PostgreSQL URL and map it to `DATABASE_URL` in SQLAlchemy `postgresql+psycopg://` form. Limit database access and retain backups. Do not use demo seed records with real student data.
2. Register two public OIDC clients with the college provider: dashboard redirect `https://YOUR_VERCEL_DOMAIN/` and Android redirect `focuslock://oidc/callback`. Configure an API audience that receives RS256 JWT access tokens. Set `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `OIDC_AUTHORIZATION_ENDPOINT`, `OIDC_TOKEN_ENDPOINT`, both client IDs and both redirects. The server checks exact issuer/audience/signature; obtain issuer metadata from the college, not guessed values.
3. In Vercel environment settings, enter production secrets from `.env.production.example`: `APP_ENV=production`, `ENABLE_DEV_AUTH=false`, `DATABASE_URL`, independent 32+ byte `QR_SIGNING_KEY`, `POLICY_SIGNING_KEY`, `BLE_TOKEN_KEY`, exact `RESOURCE_ALLOWED_HOSTS`, OIDC fields, `CRON_SECRET` (random 16+ bytes), and retention days. Keep `DEV_PASSWORD` and `DEV_RECEIVER_TOKEN` unset. For Play Integrity, set `PLAY_INTEGRITY_MODE=off` or `optional` until the Android token acquisition and Google Cloud project are validated; store service account JSON only in a secret environment variable. Do not commit it.
4. Run `alembic upgrade head` **against the managed database** from an operator-controlled environment using the production `DATABASE_URL`, then `alembic check`. Migrations are not run in the request path or Vercel build. On a new empty production database, verify the initial administrator's exact OIDC subject and run `python -m app.provision_admin --subject SUBJECT --email EMAIL --name NAME`. This is a one-time bootstrap; later users are added by an authenticated admin.
5. Deploy the repository as a Vercel Services project. Check `/api/health/live`, `/api/health/ready`, dashboard HTTPS, OIDC code/PKCE callback, assigned-course access, QR check-in, teacher confirmation, data requests and retention cron. Verify the dashboard's callback URL is exact and that Vercel function/platform logs omit tokens and sensitive query data. Set the Android release build's `-PRELEASE_API_BASE_URL=https://YOUR_VERCEL_DOMAIN/api` and real `RESOURCE_ALLOWED_HOSTS`; install only through a controlled test channel until physical-device and Play policy validation finish.

The user signed in to a Vercel Hobby account on 11 October 2026. Its Storage screen lists marketplace PostgreSQL providers, but none was connected. The user confirmed that neither a managed database nor college OIDC details are ready, so no public deployment or end-to-end production identity test was performed. Creating a marketplace database may require accepting that provider's legal terms; this has not been done. The app should not receive real student data until the college completes identity, security, retention, consent and device review. Vercel is the hosting target, not a claim of legal compliance or Play approval.
